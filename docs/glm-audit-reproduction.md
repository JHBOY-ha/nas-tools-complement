## 原报告需要修正的解释

### 代理配置是字典

`Config.get_proxies` 返回配置值，正常 Web 配置入口将其构造成包含 http/https 的字典。TMDB setter 再手工拼成 Python 字典表达式字符串。shell 注入使用代理值中的 shell 元字符；Python 注入则需要利用 setter 未转义单引号的行为，从字符串字面量逃逸。分号或 `$()` 出现在正常 Python 字符串内部，并不会单独导致 Python 执行。

证据位置：`config.py:152`、`web/action.py:319`、`web/action.py:1186`、`app/media/tmdbv3api/tmdb.py:73`、`:142`、`:164`。

### JWT 存在缓存失效条件

`TokenCache` 是进程内缓存，TTL 为 4 小时、容量 256。JWT 默认有效期为 2 小时。客户端提交的原 token 作为缓存键，认证检查的是该键对应的最新 JWT；续签只替换缓存值，不要求客户端更换原 token。过期后续签会重置该键的缓存 TTL，因此在缓存失效前持续触发续签可以延长会话超过 4 小时。**4 小时不是会话总时长上限，也不是每次请求都刷新 TTL。** 原键自插入或最近一次续签起超过 TTL、被删除、容量淘汰或进程重启后，旧 token 无法借这条路径恢复。原报告的“永不过期”应改成“缺少绝对会话期限，过期 JWT 在缓存存续期间仍可用作续签入口”。

证据位置：`app/utils/cache_manager.py:12`、`web/security.py:108`～`:115`、`web/apiv1.py:98`。

### 刷流规则求值的输入边界不同

预先篡改数据库的 `RSS_RULE` 后，真实 `__brushtask_detail` 可以执行表达式，已用进程标记验证。但普通 `__add_brushtask` 先构造 dict，数据库写入再使用 `str(dict)`；测试将表达式作为 include 字符串提交，求值时仍只是普通字典值，没有执行。未证明普通表单可直接向该数据库字段写入完整的恶意表达式。

因此可以确认危险的数据库求值设计，但不能把它与 `test_connection` 任意输入直接求值视为同样的攻击链。报告中的“后门”也不能证明作者意图，技术结论是用户可控的任意表达式执行。

证据位置：`web/action.py:1934`、`:2040`、`:2041`、`app/helper/db_helper.py:1790`、`:1791`、`app/brushtask.py:116`、`:117`。

## 本地 Git 历史对照与归因边界

基线使用本仓库无父提交的初始快照 `f4a61594736819fddb06694b1f1b72814de994ec`，与当前 `ca5919f` 对照。这不是已验证的外部上游版本；本轮没有联网取得上游仓库，也没有把 `origin/master` 当作上游，因为它指向当前 fork。

- **报告列举的敏感命令并非后续才出现。** 初始分发表已有 `user_manager`、`update_config`、`update_system`、`rename_file`、`import_custom_words`、`test_connection`。`action_login_check`、`WebAction.action`、用户管理、重命名、词包导入及偏移求值的方法 AST 与初始快照相同。`update_system` 后续只修改 fetch refspec，代理 shell 插值原已存在；`test_connection` 后续增加临时配置参数，两处 `eval` 原已存在。不能据此称这些风险均由本 fork 后续新增，也不能倒推一定来自外部上游。
- **分发表确有扩展，但不能只凭新增命令就宣称新增 RCE。** 相对初始快照增加 `special_confirmation`、`speed_test`、`test_opensubtitles`、`openclaw_qr_start`、`openclaw_qr_status` 五个命令。本轮未逐个执行这五个命令或审计所有内部保护，因此不对它们各自的完整影响作新结论。
- **多个现有问题可追溯到初始快照。** 推荐模板的 `Params|safe`、JWT 认证/续签、TokenCache 的 4 小时 TTL 与 256 容量、刷流详情求值、历史季集解析、非法正则初始化、网页 query 插值和评分元组均已存在。`media.py` 的精确异常 print 写法初始及当前均为 7 处。HTTP 工具后来增加可选 TLS 校验，但默认关闭及严格 UTF-8 解码仍保留。

## 修复顺序建议

优先处理 `/do` 的服务端权限及命令 allowlist，同时移除 `test_connection` 和识别词偏移的任意表达式执行能力。只加管理员限制仍会保留恶意词包对管理员的执行风险。代理 shell 插值和手工 Python 表达式序列化应一起替换。

推荐页的脚本数据应用 `tojson` 等面向 HTML script 上下文的安全序列化；只移除 `safe` 不是完整方案，Python dict 的布尔值或 None 本来也不能直接充当合法 JavaScript JSON。

JWT 策略、历史删除顺序、非法正则、携带凭据路径的 TLS 校验和解码异常随后修复；缓存容量、查询参数和评分类型作为后续可靠性修复，重复定义与异常 print 作为维护修复。该顺序基于当前调用证据，不是按原报告颜色标签机械排序；TLS 严重度需结合具体凭据和网络环境确定。

首轮新增复现测试及核实文档；本轮仅补充本报告和 `AGENT.md`，保留既有测试，未修改业务实现、提交代码或执行部署。
